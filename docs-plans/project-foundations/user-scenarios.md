# SkillWeave Concrete User Scenarios

This document provides detailed, end-to-end walkthroughs of how SkillWeave is used in practice across coding and non-coding workflows. It illustrates the exact problems users face, the verbatim dialogues between users and their agents, the output generated by SkillWeave, and how the tool successfully unblocks them.

---

## Telemetry, Interfaces, and Learning Dynamics

### 1. How and When Logging Begins (The Original User's Path)
- **Log Initiation:** Logging begins automatically when a builder registers an active task session. This can be done via:
  - *CLI Agent/Skill commands* (e.g. `weave start [task-name]`).
  - *Automatic Workspace Activation* (when the VS Code extension detects active edits in a tracked Git repository).
  - *Browser Extension detection* (when the Chrome extension detects the user chatting on a generative AI domain like Claude or ChatGPT).
- **Telemetry Capture:** Because SkillWeave is built as an **MCP (Model Context Protocol) Server**, it functions as a centralized gateway. It listens to:
  1. *Workspace File Diffs:* Monitors git changes and saves in the project workspace.
  2. *Compiler Stack Traces:* Captures console log execution stack traces and build failures.
  3. *AI Client databases:* Extracts prompt histories directly from Cursor/Copilot local databases or browser chat tabs.
- **The Role of the Reflection:** When the task is complete (or when stuck), the user submits their session via the VS Code sidebar button, CLI command, or Slack channel bot. They write a 2-minute post-session reflection. This is critical because:
  - It forces the original user to cognitively synthesize their trial-and-error, solidifying their own learning.
  - It translates raw code changes into conceptual "steering guidelines" (e.g. *"I had to tell the agent to use Auto-Layout instead of X/Y"*).
  - The NLU search engine uses this text as vector index metadata to match future stuck developers.

### 2. What the Current User Sees (Progressive Disclosure)
To prevent cognitive overload, the current user is never thrown a massive, raw 4-hour chat transcript. Instead, the UI follows a **progressive disclosure model**:
- **Level 1 (Immediate Hover / Alert Card):** When a user gets stuck, they see a tiny, 2-line preview in their tooltip or sidebar card. It shows the peer's problem summary and the **Pivot Prompt**—the exact single line of instruction that unblocked the original user.
- **Level 2 (Sidebar Panel):** If the user clicks for more detail, the sidebar displays the original user's NLU reflection (explaining *why* the pivot prompt was necessary) and the **Diagnostic Questions**.
- **Level 3 (Streamlined Timeline):** If they still need context, they can expand the timeline. The chat log is shown with redundant exchanges collapsed, displaying only the key code files changed. The full raw dialogue of the 4-hour session is accessible only via a dropdown drawer if they need low-level code parameter details.

### 3. When and How Diagnostic Questions are Answered
- **No Database Submissions:** The current user **does not write answers to the diagnostic questions in a form**, nor are they submitted to the database.
- **Forcing Functions for Prompting:** The diagnostic questions are active self-check forcing functions. They are displayed in the sidebar to make the user think about their current state before they type. 
- **Prompt Construction:** The user reads the diagnostic questions (e.g., *"Did you wrap the cards in a parent frame?"*), checks their editor, and uses the answers to write their next prompt to their own agent (e.g. *"Yes, I see the cards are not in a parent frame. Agent, group these cards into a parent Auto-Layout frame..."*). The only question the current user answers in the database is their own post-session reflection when they submit their completed task.

### 4. Multi-User Scaling & The Synthesis Progression (Ranking and Aggregation)
What happens when multiple peers have resolved the same error? Showing all logs would clutter the UI, especially in a large organization.
- **Small Cohort (N = 1 or 2):** The sidebar displays the case studies as separate, selectable tabs (e.g., `[Case Study A: Sarah (Figma)]`, `[Case Study B: Chloe (Figma)]`).
- **Large Cohort (N >= 3):** The system triggers the **Meshed Wiki Synthesis**. An offline LLM process aggregates all similar logs into a single structured page containing common root causes and resolution prompts, followed by clickable anchors to the individual peer logs.
- **Scaling to Large Groups (N >= 10):**
  If a problem has been encountered and resolved by 10+ people, showing all of them is too overwhelming. SkillWeave implements **Utility-Based Ranking** to select the top **3 most relevant case studies** to display as anchors, collapsing the remaining logs into a searchable archive drawer:
  1. *Resolution Velocity:* How quickly did the peer resolve the issue after typing their Pivot Prompt? (Higher velocity = more effective prompt).
  2. *Reflection Quality (NLU Scored):* Reflections containing richer, more analytical explanations of *why* the fix worked are ranked higher.
  3. *Peer Upvotes:* Teammates can mark a peer recipe as "Helpful" on their shared cohort dashboard.
  4. *Delta Simplicity:* Fixes that resolve the error with clean, concise code/text modifications (rather than large, sprawling refactors) are prioritized.

### 5. Similarity Matching Pipeline (How matches are determined)
A user's problem does not need to be identical to a peer's for SkillWeave to suggest a match. The local MCP server runs a **Four-Stage Similarity Matching Pipeline** to qualify and rank potential matches:
1. **Static AST & File Context (Relevance Weight: 25%):**
   - SkillWeave checks what files the user has open and is currently editing (e.g., `app.routes.ts`, `auth.service.ts`).
   - If the file names, directory structures, or imported library dependencies (e.g. `@angular/router`, `axios`) match past logs, the match score increases.
2. **Error Signature Matching (Relevance Weight: 35%):**
   - If the local compiler or terminal outputs an error, SkillWeave parses the stack trace to extract the unique error code signature (e.g., `403 Forbidden`, `NG0301: Component...`, or a specific TypeScript compiler error ID).
   - It matches these exact signatures against the error history database.
3. **NLU Semantic Embeddings (Relevance Weight: 30%):**
   - SkillWeave takes the user's latest 3 chat prompts with their local agent and generates a text embedding vector (using a lightweight local embedding model).
   - It computes the cosine similarity between this vector and the database of past peer Pivot Prompts and Reflections. This catches semantic matches (e.g., matching "responsive sizing" to "cards overlapping on mobile").
4. **Milestone / Process Context (Relevance Weight: 10%):**
   - SkillWeave checks what active skill template is being run (e.g., `/feature-harden-implement` or `/define-product`).
   - It prioritizes matches that occurred during the execution of the same workflow milestone, as teams are likely facing the same structural boundaries.

### 6. Safeguarding Exploration vs. The "Copy-Paste" Automation Trap
A major risk in peer-learning tools is the "single-mind bias"—if a user is shown a single peer's working solution, they might copy it blindly without exploring alternative architectures, harming their own learning. This risk is especially critical in tasks requiring deep thinking, planning, and research (such as drafting a thesis, designing system structures, or scoping products), where there is no single "correct" output. The tool is designed to scaffold a builder's *own* reasoning process rather than leading them to replicate a peer's identical conclusion.

SkillWeave enforces this divergent exploration through four deliberate design constraints:
- **No Direct Code or Text Copy-Pasting:** The tooltips and sidebars do *not* display copy-pasteable blocks of the peer's final code or written text. They only display the **Pivot Prompt** (the steering instruction) and the **Diagnostic Questions** (the underlying concept). 
- **Multi-Angle Contrast Panels:** For planning and research milestones, the sidebar does not present a single "best" solution. Instead, it dynamically clusters and presents **contrasting peer perspectives** (e.g., showing how Team A resolved a value proposition challenge by focusing on learner-sourcing while Team B resolved it by focusing on Socratic tutoring). This forces the builder to compare different design trade-offs.
- **Socratic Contrast Prompts:** When presenting peer cases, the tool generates comparative prompts: *"Peer Aubrey chose to prioritize a Learner-Sourcing telemetry model to resolve this. How does your project's focus (e.g. Socratic routing) adapt or push back against that decision?"* This triggers critical comparison rather than blind alignment.
- **Cognitive Translation & NLU Verification:** The NLU quality gate evaluates the user's own reflections before allowing a commit. For thinking-heavy tasks, the gate checks that the reflection contains *unique project-specific vocabulary* and explicitly rejects submissions that show high lexical or structural similarity to peer logs. The builder must articulate *their own* rationale, ensuring divergent outcomes are preserved.

### 7. Multi-Modal Artifact Sourcing & Cross-Platform Deep-Linking
For tasks operating on different platforms (such as code editor environments, design canvases, database clients, or academic writing tools), a raw text chat log is often insufficient to fully communicate the peer's resolution. SkillWeave resolves this by automatically capturing and delivering **platform-specific complementary materials** alongside the dialogue transcript and NLU reflections:

#### Category 1: Web Development & Frontend Workflows (e.g. React, Angular)
- **Interactive Code Sandboxes:** The sidebar displays a link to open a sandboxed container (e.g., StackBlitz or CodeSandbox) containing the peer's specific modified component. The user can interact with the rendered localhost page and edit the code in real-time without affecting their main workspace.
- **Localhost Snapshots & Video Clips:** When the original user runs `weave submit`, the IDE background process captures a high-resolution screenshot or a 5-second video recording of their local host window. The current user can click the sidebar image card to see exactly how the resolved component behaves (e.g., verifying that a dropdown menu opens and registers focus rings).
- **Line-by-Line Code Diffs:** Displays a clean, highlighted Git diff showing exactly which lines of code were modified (e.g., showing the Axios cache interceptor configuration changes side-by-side).

#### Category 2: Visual Design Workflows (e.g. Figma, Canva, Miro)
- **Visual Image Comparison Slider:** The Figma plugin exports PNG snapshots of the modified frame canvas. Next to the Pivot Prompt, SkillWeave displays an image slider showing the exact layout before the fix (overlapping elements) and after the fix (clean grid).
- **Structural Node-Tree Deltas:** Visualizes the layer node tree transition (e.g. showing sibling frames wrapped under a parent `[Auto-Layout Frame]` wrapper node).
- **Direct Canvas Deep-Linking:** The sidebar contains a direct node link (e.g., `https://figma.com/file/XYZ?node-id=123:456`). The current designer can click it to jump straight to the peer's canvas frame to inspect the layout properties panel live in read-only mode.

#### Category 3: Database & Backend Workflows (e.g. Firestore, PostgreSQL, Supabase)
- **Database Schema ER Diagrams:** Displays a visual Entity-Relationship (ER) diagram delta (e.g., showing how Team A added a new foreign-key relation to resolve a database constraint loop).
- **Interactive API Sandboxes:** If the peer resolved an API route issue, the sidebar displays an interactive Swagger or Postman playbook execution block, allowing the current user to trigger test endpoints and view actual JSON response formats.

#### Category 4: Academic Writing & Planning Workflows (e.g. Markdown, LaTeX, Google Docs)
- **Document Text Diff Highlights:** Displays visual color-coded text diffs highlighting structural rearrangements, outline additions, or vocabulary replacements (e.g. green highlighting for added paragraphs and red strike-throughs for deleted startup-jargon phrases).
- **Compiled PDF Outline Comparisons:** Renders a side-by-side outline tree comparing the document structure changes.

### 8. Resolution Detection & Slicing Telemetry
To capture clean, focused peer logs without manual start/stop friction or massive 4-hour chat dumps, SkillWeave implements a passive-active hybrid telemetry system that detects stuck states, slices log segments, and confirms resolutions:

#### A. Starting the Log Buffer (Friction Triggers)
SkillWeave runs a passive local daemon that only starts recording dialogue history and code diffs in a temporary buffer when a **friction trigger** is detected:
1.  **Linter/Compiler Crash:** The local workspace watcher detects compile errors (e.g. `Angular compilation failed`, `AxiosError: 403`, or linter rules blocking git commits).
2.  **Dialogue Repetition Loop:** The builder sends $\ge 3$ prompts to their agent within a rolling 10-minute window without making modifications to the underlying code files, indicating the builder is stuck in a prompt steering cycle.
3.  **Command Execution Loops:** The builder runs the same command line sequence (e.g. test suites or database migrations) three or more times consecutively with failing results.

#### B. Slicing the Dialogue Segment (Message-Count Windowing)
Once recording is triggered, SkillWeave maintains a rolling **Message-Count Window**. When the issue is resolved, the system slices the transcript from the first friction trigger back-buffered by $N=2$ turns. Slicing by message count instead of time ensures that the context is preserved even if the builder takes a 2-hour break or pauses to research documentation.

#### C. Static Dependency Grafting (Prerequisite Preservation)
To prevent context loss where imports or setups were defined hours before the sliced window, the system analyzes the code diff generated at the moment of resolution. If it detects imports, types, or variables that were introduced earlier in the active session but fall outside the sliced message window, it runs a dependency check to locate their creation. The system then automatically extracts those specific turns and grafts them as a **"Prerequisite Context"** card at the top of the timeline.

#### D. Resolution Confirmation & Popup Gating
To prevent false positives (such as when a builder deletes their broken code or abandons a task, causing tests to pass without solving the actual problem), SkillWeave uses a non-blocking confirmation gate:
1.  **Intent Detection + Compile Success:** When the compiler errors clear and unit tests pass, OR the user enters a positive NLU resolution phrase (*"that worked," "it runs," "fixed it"*), SkillWeave triggers a micro-toast alert.
2.  **The Toast Alert:** A slide-in popup appears in the corner of the sidebar: 
    `💡 Did that last step resolve the issue? [Yes: Save Log] [No: Keep Working]`
3.  **The Gating Action:** 
    - If the user selects **[Yes]**, the log segment is locked, the user is prompted to enter a 2-minute steering reflection, and the case study is prepared for validation.
    - If the user selects **[No]** (or ignores the toast, which auto-dismisses in 30 seconds), the system keeps buffering, assuming the work is still in progress.

## The Log Credibility & Validation Mechanism
To ensure that peer transcripts suggested to users are successful and credible, SkillWeave validates every logged session before indexing it in the community database. A log is marked as a **Successful Case Study** only when it satisfies three automated validation gates:
1. **Compilation and Automated Verifications:** The file deltas generated during the session must build successfully and pass all local test suites (e.g. unit tests, linting, or schema validation scripts).
2. **Post-Session NLU Reflection Gate:** The builder must submit a post-task reflection through the CLI or editor. The local NLU gate evaluates the response to ensure it is understandable and directly describes a moment of *surprise* (unexpected agent behavior) and *reframing* (how they steered it), rejecting low-effort placeholders.
3. **Stability Delta:** The local watcher monitors the modified lines of code or text. If those same lines are not modified or reverted for the next 2 hours of active work, the solution is deemed stable.

## Scenario E: Figma UI Spacing & Grid Alignment (Design)

### 1. The Original User's Path
*   **Original User:** Sarah (UI Designer on Team "BrandBoard")
*   **The Problem:** Sarah was using a Figma generative design agent to lay out three dashboard cards. The agent kept generating absolute pixel coordinates and static positions, causing the cards to overlap and break whenever the parent container was resized.
*   **Verbatim Chat Log (Original User & Figma Agent):**
    > **Sarah:** *"I want to layout three dashboard cards side by side in the main container frame. Make them look nice and clean."*
    >
    > **Figma Agent:** *"I have placed three frames at absolute coordinates inside the parent frame: Card 1 at X=10, Y=20; Card 2 at X=400, Y=20; Card 3 at X=790, Y=20. Spacing is set to 8px. Let me know if you need any adjustments."*
    >
    > **Sarah:** *"Wait, when I resize the parent frame to test mobile or tablet sizes, the cards overlap. Make the layout responsive so they stretch dynamically."*
    >
    > **Figma Agent:** *"I have recalculated the absolute positions for a parent width of 1440px: Card 1 is at X=20, Card 2 at X=480, Card 3 at X=940. I can calculate positions for other specific sizes if you tell me the target width."*
    >
    > **Sarah:** *"No, I don't want you to keep recalculating coordinates! I want them to resize automatically when the container stretches."*
    >
    > **Figma Agent:** *"I cannot predict all container resize values dynamically. I will change the default card widths to a fixed 450px and offset their margins."*
*   **Sarah's Resolution:** Sarah realized the agent was failing because it didn't know about Figma's native layout engine. She bypassed the absolute coordinates by prompting:
    > **Sarah (Pivot Prompt):** *"Group the three cards into a parent frame. Apply horizontal Auto-Layout to the parent frame with wrap enabled, and set all children card widths to Fill Container instead of fixed pixels."*
    >
    > **Figma Agent:** *"I have wrapped the three cards in a new parent frame. Applied horizontal Auto-Layout, enabled wrap, and set child sizing constraints to Fill Container. The cards now dynamically stretch to share the parent frame width and wrap to the next line on narrow screens."*
*   **Sarah's Reflection (CLI Gating):**
    > *"Figma agent kept generating absolute coordinates for cards, causing overlaps on resize. Steered it by grouping them into a parent Auto-Layout frame and setting child widths to Fill Container."*
*   **How SkillWeave Validated the Log:**
    - *Verification:* The local Figma plugin inspected the generated design file's JSON node. It verified that the parent frame contained `layoutMode: "HORIZONTAL"` and children frames had `layoutAlign: "INHERIT"` and `layoutGrow: 1` (Figma's API flags for Fill Container).
    - *NLU check:* Sarah's reflection was validated as high quality (identified absolute position surprise and Auto-Layout reframing).
    - *Stability:* The cards' layout properties remained unchanged for the rest of the design session. The log was indexed.

## Scenario F: Academic Paper Citation Hallucinations (Research)

### 1. The Original User's Path
*   **Original User:** Daniel (Graduate Researcher on Team "LitReview")
*   **The Problem:** Daniel was using a literature review agent to compile a summary of a PDF paper on conversational interfaces. The agent kept generating realistic-looking citations that did not exist in the PDF paper, pulling papers from its pre-trained weights.
*   **Verbatim Chat Log (Original User & Lit Agent):**
    > **Daniel:** *"Summarize the attached paper on conversational agency and cite the relevant sections."*
    >
    > **Lit Agent:** *"The paper outlines the concept of reflective scaffolds... (Bernstein et al., 2024; Wood, 1976). This model suggests that..."*
    >
    > **Daniel:** *"Wait, I just checked the bibliography at the end of the PDF. There is no paper by Bernstein et al. 2024. Why did you cite it?"*
    >
    > **Lit Agent:** *"My apologies. The correct citation is Bernstein et al., 2022. The paper discusses..."*
    >
    > **Daniel:** *"No! There is no Bernstein paper of any year in this PDF's references list. Stop guessing."*
    >
    > **Lit Agent:** *"I apologize. The correct reference is Wood et al., 1976. I will replace the incorrect citation in the summary."*
*   **Daniel's Resolution:** Daniel realized the agent was treating the task as a general writing task, letting its pre-trained weights bleed in. He constrained the agent's citation boundaries:
    > **Daniel (Pivot Prompt):** *"Do not cite any papers from your pre-trained weights. Only extract inline bracketed footnotes ([^authorYear]) matching the exact bibliography items present in the references list at the end of the attached PDF."*
    >
    > **Lit Agent:** *"Summary regenerated. Bounded citations strictly to the PDF's references bibliography: (Wood et al., 1976; Schön, 1983)."*
*   **Daniel's Reflection (CLI Gating):**
    > *"Lit Review agent hallucinated external citations from its weights. Steered it by telling it to only cite items present in the PDF references bibliography using footnote markers."*
*   **How SkillWeave Validated the Log:**
    - *Verification:* A local citation auditing script scanned the generated markdown file and cross-referenced all bracketed citation keys against Daniel's `literature.bib` file. All citations were found to be authentic.
    - *NLU check:* Reflection successfully described the hallucination surprise and the bibliography-bounding prompt reframing.
    - *Stability:* The citations list passed without modifications for the next 2 hours. Log indexed.
